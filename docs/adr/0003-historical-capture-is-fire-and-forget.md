# Historical Capture is fire-and-forget from the browse UI

Triggering a Historical Capture (a backwards pull of earlier Group Messages) from the Historical Browse modal returns immediately and runs the pull on a backend `@Async` thread, with no progress feedback to the browser. The operator must manually re-query the modal to see newly captured messages. The pull reuses `saveBySince(gid, sinceTime, beforeMid)` - now itself `@Async void` - with `beforeMid` left null so the method resolves the local `min_mid` itself and skips already-captured messages rather than re-fetching them from Weibo; an empty group (no local messages, `min_mid == 0`) falls back to a null cursor and fetches the latest batch first.

The `POST /chat/since` endpoint is the single entry point: it binds gid and a Shanghai-time `sinceTime`, delegates to `saveBySince`, and returns `204 No Content` without waiting. There is no separate capture endpoint - `saveBySince` serves both the (now async) historical-capture path and retains its lock-protected backfill loop. Chosen because the alternatives were worse for a single-user local tool. A synchronous blocking call would hang the HTTP request for minutes while the pull loop sleeps 200-2000ms per page against Weibo rate limits; an async-task-plus-progress-polling scheme would add a task-status store and a polling endpoint for a feature whose result the operator can see by re-running a local query. Fire-and-forget keeps the surface to one endpoint and one button. Resolving `min_mid` inside `saveBySince` (rather than in a wrapper) means every caller benefits from skipping the already-captured range, which the loop would otherwise re-walk from the newest message whenever `beforeMid` is null (insertIfAbsent keeps it correct, just wasteful).

The surprising part a future reader must understand: `saveBySince` is `@Async void`, so neither its `SaveResult` nor any exception reaches the caller - the HTTP layer always returns 204, even when `saveBySinceLock.tryLock()` loses to a concurrent capture and pulls nothing, and the UI gives no signal that the capture finished or how much it fetched. Each pulled page is logged (`群 {gid} 历史同步：新增消息 {n} 条，忽略 {n} 条，最旧消息时间 {ts}`) so progress is observable in server logs only. Both choices are deliberate, because in this tooling the operator re-checks the browse list and the next periodic `SyncTask` run is unaffected.

# Media Send ships image first, video in a later phase

The first phase of Media Send implements image sending only: paste or pick a local image, upload it to Weibo through the three-step init -> uploadx -> send_message chain, and re-pull it into the local store via `saveIncremental`. Video is deferred to a second phase. Both phases share the same front-to-back upload channel and the same `send_message.json` send step, but video adds a cover-image upload, `multimedia/init` with `mediaprops` (width/height/duration), chunked `application/octet-stream` upload to a separate CDN host, and dual MD5 (whole-file plus per-chunk) - roughly double the moving parts of image alone.

Chosen because shipping image first validates the whole new channel (frontend multipart -> `WeiboHttpClient.postMultipart` -> Weibo init/uploadx/send -> `saveIncremental` re-pull) with the smallest blast radius, and every piece video needs is either an extension of the image path (the upload channel, the send step) or cleanly separable (cover extraction, `mediaprops`, the chunked octet-stream uploader). Doing both at once would entangle two unrelated failure surfaces (a cover-extraction bug versus an upload-channel bug) and force a single large review instead of two small ones. The surprising part a future reader must understand: `clientid` in the `send_message` `annotations` is intentionally omitted in phase one - the existing text-send path omits the entire `annotations` field and succeeds, so the image path sends `{"webchat":1}` only and relies on the real Weibo response to tell us whether `clientid` is required; if Weibo rejects it, `clientid` is added in a follow-up rather than blocking the whole feature on a reverse-engineered web-client session id.

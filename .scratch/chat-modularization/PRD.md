# 群聊页面模块化

创建日期：2026-09-06。

工作分支：`codex/chat-modularization`。

## 问题与目标

当前群聊页面的 `chat.js` 约 2,235 行，同时承担群列表、会话消息流、编辑器、Historical Browse、Analysis、Return Celebration、登录和页面调度。大部分状态和 DOM 引用集中在一个闭包中，消息展示还会读取当前群并直接打开庆祝浮层。仅移动函数而保留共享状态，无法改善功能修改时的影响范围。

将页面整理为一个入口、七个功能模块和一个公共模块。用户仍通过原页面完成相同操作，维护者能够在对应模块中修改功能，并通过现有浏览器测试验证完整路径。

## 已确认的实施范围

1. 保持原生 JavaScript，使用浏览器 ES Modules，不新增框架、打包器或包管理流程。
2. 每个功能拥有自己的可变状态、DOM 引用、事件和异步资源。入口连接模块，不导出全局状态仓库。
3. 提取可供会话和 Historical Browse 共用的消息展示逻辑。
4. 保持后端端点、请求参数、持久化数据格式、页面路径及样式契约。
5. 各次提取都保持页面可运行，通过完整功能路径验收。
6. 建议把直接关联模块生命周期的问题纳入验收：Analysis 的过期响应和视图竞争，切群后的旧消息 DOM、媒体回调和庆祝浮层残留，Historical Capture 的晚到提示，以及发送完成回调的群归属。每类修复先写失败测试，再以独立修复提交实施，和机械迁移提交分开。

第 6 项是相对纯拆文件方案的明确行为调整，已随任务拆分获得用户确认。其他已知问题记录在详细设计中，不默默纳入实施。

## 保持的领域行为

- View Refresh 只读本地数据，不启动 Background Capture，不请求微博拉取消息。
- Catch-up 在页面重新可见时，从已有消息边界补齐后续本地消息，保留阅读位置。
- Historical Browse 的筛选、上下文和滚动不影响主会话。
- Historical Capture 通过既有接口异步启动，前端不新增进度轮询。
- Media Proxy 保持相对代理地址和按需读取；媒体可用性不作离线保证。
- 文本发送和 Media Send 不直接向消息存储写入或向会话插入乐观消息。
- HTTP 409 仍表示消息已发出但本地同步失败，保留编辑内容并提示，不自动重发。
- Return Celebration 在首屏建立基线，在新到达消息上判定，切群取消旧动画。
- Credential 登录继续使用现有扫码与二维码内嵌展示，不新增后端取消接口。

## 不做的事项

- 不迁移 TypeScript，不引入状态管理库、事件总线或通用控制器基类。
- 不重写 CSS、页面布局、后端接口或数据库结构。
- 不新增虚拟列表、消息缓存上限、预加载策略和性能承诺。
- 不新增分群草稿、后台分析任务管理界面和持久化格式迁移。
- 不以每个文件的行数作为完成指标。

## 成功标准

- [ ] 九个自有源码文件职责明确，现有第三方脚本和素材保持原位置。
- [ ] 功能模块没有循环导入，不访问另一模块的内部可变状态。
- [ ] 入口不操作消息 Map、历史游标、附件文件、分析报告或庆祝名单。
- [ ] 同一功能的事件只注册一次，重复登录初始化不会增加轮询或事件监听。
- [ ] 已迁移模块在每一步均可通过页面功能演示，不等待最后一票才恢复可用。
- [ ] 群聊浏览、媒体、发送、历史、分析、庆祝及登录回归测试通过。
- [ ] 关联行为修复具有先失败后通过的测试证据，未授权的其他优化未混入。
- [ ] 打包结果包含全部模块，浏览器加载无模块解析、路径或 MIME 错误。

# 群消息与微博本地查询接口

Status: ready-for-agent

## Problem Statement

用户希望基于本地已采集的群消息和微博数据构建浏览页面，但当前后端接口尚不能完整支持页面所需的组合筛选与视频访问。群消息只能按群和时间分页，不能按发言人姓名或正文搜索；群视频没有可供前端使用的本地视频地址，且没有完整覆盖参考数据中的视频类型。微博可以按博主和时间筛选，但不能按当前微博及转发微博正文搜索，也没有直接跳转当前原微博的明确链接字段。

## Solution

扩展现有群消息和微博列表接口，不新增独立搜索接口。群消息列表增加可选的发言人精确匹配和正文字面包含匹配；微博列表增加覆盖当前正文与转发正文的字面包含匹配。两个列表继续使用本地数据、稳定倒序和分页。

保留现有消息类型字段，由调用方使用 `msgType`、`msgTypeName`、`mediaType` 和 `text` 判断显示方式。补齐非红包 `mediaType = 13` 的视频处理，返回本地视频代理 URL，并让视频代理使用流式响应和 HTTP Range。当前微博增加后端生成的原微博链接；转发微博不增加链接。

## User Stories

1. 作为本地群消息浏览者，我希望取得本地群聊列表，以便选择要查看的群。
2. 作为本地群消息浏览者，我希望按群分页查询消息，以便处理消息量较大的群聊。
3. 作为本地群消息浏览者，我希望显式提供页码和每页数量，以便调用行为没有隐含分页状态。
4. 作为本地群消息浏览者，我希望不提供时间条件也能查询消息，以便浏览该群的全部本地消息。
5. 作为本地群消息浏览者，我希望只提供开始时间，以便查询该时刻及之后的消息。
6. 作为本地群消息浏览者，我希望只提供结束时间，以便查询该时刻及之前的消息。
7. 作为本地群消息浏览者，我希望同时提供起止时间，以便查询包含两个边界的时间范围。
8. 作为本地群消息浏览者，我希望时间按上海时区解释，以便页面输入与本地时间一致。
9. 作为本地群消息浏览者，我希望按完整发言人姓名精确筛选，以便同一姓名的消息被一致返回。
10. 作为本地群消息浏览者，我希望按正文关键词做包含匹配，以便找到正文中包含该文字的消息。
11. 作为本地群消息浏览者，我希望 `%`、`_` 和转义字符按普通文字搜索，以便输入不会意外变成数据库通配规则。
12. 作为本地群消息浏览者，我希望群、时间、姓名和正文条件按 `AND` 组合，以便逐步缩小结果。
13. 作为本地群消息浏览者，我希望第一页优先返回最新消息，以便快速看到最近内容。
14. 作为本地群消息浏览者，我希望相同时间的消息仍有稳定顺序，以便翻页时结果可预测。
15. 作为本地群消息浏览者，我希望结果包含准确总数，以便页面计算分页状态。
16. 作为本地群消息浏览者，我希望每条消息保留原始消息类型和媒体类型，以便根据微博消息语义选择显示方式。
17. 作为本地群消息浏览者，我希望 `mediaType = 13` 的红包和视频能够被正确区分，以便红包不会被当作视频。
18. 作为本地群消息浏览者，我希望图片消息继续提供缩略图与原图 URL，以便先预览再查看大图。
19. 作为本地群消息浏览者，我希望视频消息在有封面时提供缩略图 URL，以便在打开视频前识别内容。
20. 作为本地群消息浏览者，我希望没有封面的视频返回空缩略图 URL，以便调用方使用统一占位图。
21. 作为本地群消息浏览者，我希望视频消息提供本地代理 URL，以便上游地址和 Credential 不暴露给调用方。
22. 作为本地群消息浏览者，我希望视频能边传输边播放，以便大文件不必全部载入内存。
23. 作为本地群消息浏览者，我希望视频支持 HTTP Range，以便浏览器快速开始播放并拖动进度。
24. 作为本地群消息浏览者，我希望每条消息继续包含发言人姓名和头像，以便识别消息发送者。
25. 作为本地微博浏览者，我希望取得本地博主列表，以便选择一个或多个博主。
26. 作为本地微博浏览者，我希望不提供博主条件也能查询所有本地微博，以便跨博主浏览。
27. 作为本地微博浏览者，我希望按一个或多个博主筛选，以便集中查看选定博主的微博。
28. 作为本地微博浏览者，我希望微博时间条件与群消息使用相同的上海时区和包含边界语义，以便两类页面行为一致。
29. 作为本地微博浏览者，我希望按关键词搜索当前微博正文，以便找到博主发布的相关内容。
30. 作为本地微博浏览者，我希望关键词也搜索页面展示的转发微博正文，以便按被转发内容找到对应微博。
31. 作为本地微博浏览者，我希望关键词只匹配两段可见正文，而不是任意结构化 JSON 字段，以便避免无关命中。
32. 作为本地微博浏览者，我希望博主、时间和关键词条件按 `AND` 组合，以便精确筛选微博。
33. 作为本地微博浏览者，我希望当前正文或转发正文任一匹配即可满足关键词条件，以便符合页面可见内容的搜索预期。
34. 作为本地微博浏览者，我希望微博按发布时间和微博 ID 稳定倒序，以便第一页显示最新微博。
35. 作为本地微博浏览者，我希望微博列表保留默认分页参数，以便现有调用方不受破坏。
36. 作为本地微博浏览者，我希望微博图片继续提供缩略图和原图 URL，以便先预览再查看大图。
37. 作为本地微博浏览者，我希望当前微博直接包含原微博 URL，以便调用方不需要了解微博链接拼接规则。
38. 作为本地内容浏览者，我希望所有列表数据继续只从本地数据库读取，以便筛选不会触发上游采集。
39. 作为本地内容浏览者，我希望媒体仍通过受控的本地代理按需获取，以便沿用现有 Credential 和媒体边界。
40. 作为接口维护者，我希望未知消息类型保留原始类型码和现有兜底名称，以便新类型不会导致响应失败。

## Implementation Decisions

- 现有群列表、群消息列表、微博博主列表和微博列表模块继续作为公开接口，不增加独立搜索模块或搜索端点。
- 群消息列表接口要求 `gid`、`page`、`size`，其中 `page` 必须大于等于 `1`，`size` 必须介于 `1` 和 `100` 之间。
- 群消息列表增加可选的 `senderName` 和 `keyword`。省略或空白的可选筛选值不产生过滤条件。
- `senderName` 对已保存的发言人姓名做精确匹配。
- 群消息 `keyword` 只对消息正文做字面包含匹配。数据库通配字符必须被转义，不搜索链接卡片、模板数据、文件名或其他结构化字段。
- 群消息 `start` 和 `end` 保持可分别省略，输入格式为 `yyyy-MM-dd HH:mm:ss`，按 `Asia/Shanghai` 转为时间戳。两个边界均包含；同时存在时开始时间不得晚于结束时间。
- 群消息的所有已提供筛选条件使用 `AND` 组合。
- 群消息按 `createdAt DESC、mid DESC` 排序，分页响应继续包含群信息、消息项、页码、每页数量和总数。
- 保留现有 `msgType`、`msgTypeName`、`mediaType` 和 `text`，不增加合并类型字段。
- 消息类型继续沿用现有参考枚举。协议同步和态度更新继续不作为可浏览的 Captured Content；未知类型继续保留并使用现有兜底名称。
- `mediaType = 10` 是视频。`mediaType = 13` 在正文符合现有红包判别规则时是红包，否则是视频。
- 图片消息继续返回现有缩略图和原图代理 URL。
- 被识别为视频的消息在存在视频封面引用时返回 `previewUrl`；没有封面引用时返回空字符串，不下载视频生成首帧。
- 消息响应增加 `videoUrl`。视频消息返回指向本地群媒体代理的相对 URL，非视频消息返回空字符串。
- 群媒体代理继续使用 `gid`、`mid` 和 `variant` 定位媒体，并新增 `variant = video`。现有 `preview` 和 `original` 语义保持不变。
- 视频代理必须验证消息属于指定群且消息确实是视频，不直接接受调用方提供的任意上游 URL。
- 视频代理使用当前 Credential 请求上游媒体并流式转发，不把完整视频装入单个字节数组。
- 无 Range 请求的视频响应使用 `200 OK`，并返回正确的媒体类型、内容长度和 `Accept-Ranges: bytes`。
- 支持单个封闭范围、开放结束范围和后缀范围。有效范围返回 `206 Partial Content`、正确的 `Content-Range`、`Content-Length`、媒体类型和 `Accept-Ranges: bytes`。
- 微博上游返回有效分片但状态仍为 `200` 时，本地代理必须验证 `Content-Range` 与上游 `Content-Length`，再向调用方规范化为 `206`；不得仅按上游状态判定分片是否成功。
- 不可满足的范围返回 `416 Range Not Satisfiable`，并返回 `Content-Range: bytes */<完整长度>`。多范围响应不在本规格范围内。
- 上游 Credential 失效、限流和媒体失败继续使用项目现有的一致错误语义，不把 Credential 或上游内部信息暴露给调用方。
- 发言人头像继续使用每条消息已经保存的头像字段；不引入完整群成员模型。
- 微博列表继续支持重复的 `uids` 查询参数，并继续拒绝逗号分隔形式。
- 微博列表保留 `page = 1`、`size = 100` 的后端默认值及现有范围校验。
- 微博列表增加可选 `keyword`。关键词对当前微博可见正文和被转发微博可见正文做字面包含匹配，两者之间使用 `OR`；该关键词条件与博主、开始时间和结束时间使用 `AND`。
- 微博关键词必须转义数据库通配字符，只搜索两段正文，不将转发信息中的其他 JSON 属性视为正文命中。
- 微博 `start`、`end` 的格式、时区、可选性、包含边界和先后校验与群消息一致。
- 微博按 `createdAt DESC、postId DESC` 排序，分页总数必须反映完整组合筛选条件，不允许先分页再在内存中过滤。
- 当前微博视图增加 `postUrl`，由后端使用当前微博的 `uid` 和 `mblogId` 生成微博原文地址。被转发微博视图不增加 `postUrl`。
- 群列表、微博博主列表、微博图片代理及已有图片返回字段保持兼容。
- 所有列表查询继续只读取本地数据库。媒体代理仍依赖有效的 Weibo API 和当前 Credential，不保证离线可用。
- 本功能应以增量字段和增量筛选条件为主。唯一有意收紧的现有契约是群消息的 `page`、`size` 改为必填。

## Testing Decisions

- 测试只验证模块接口可观察到的行为，不断言内部方法调用顺序、私有辅助方法或查询实现细节。
- Controller seam 使用现有 MVC 测试方式验证群消息查询参数绑定、必填规则、时间转换、默认值、错误响应和新增 JSON 字段。
- Controller seam 验证微博列表能够绑定可选关键词，并保持现有重复 `uids`、时间和分页契约。
- Controller seam 验证视频无 Range 请求返回 `200`，有效单范围返回 `206`，不可满足范围返回 `416`，并检查相关标准响应头和实际响应字节。
- Repository seam 使用真实 SQLite 验证群消息的可选时间、发言人精确匹配、正文字面包含匹配、条件组合、总数及 `createdAt/mid` 稳定倒序。
- Repository seam 必须包含 `%`、`_` 和转义字符用例，证明关键词按字面值匹配。
- Repository seam 使用真实 SQLite 验证微博当前正文匹配、转发正文匹配、两者均不匹配、与 `uids` 和时间组合、分页总数及 `createdAt/postId` 稳定倒序。
- 微博搜索测试应证明只有转发正文命中时仍能返回微博，同时不会因为转发 JSON 的非正文字段包含关键词而误命中。
- Service / Mapper seam 验证 `mediaType = 10`、非红包 `mediaType = 13` 和红包 `mediaType = 13` 的分类行为。
- Service / Mapper seam 验证有封面视频、无封面视频、图片和非媒体消息各自的 `previewUrl`、`originalUrl`、`videoUrl`。
- 视频代理测试验证群与消息归属校验、非视频拒绝、上游错误映射、媒体类型和流未被整体缓冲。
- 当前项目中的群消息 Controller 测试、微博 Controller 测试、消息与微博 Repository 测试、消息 Mapper 测试和群媒体服务测试作为新增测试的先例。
- 回归测试应证明群列表、博主列表、图片缩略图、图片原图、未知消息类型和既有分页行为未被破坏。

## Out of Scope

- 任何前端页面、前端框架、页面布局或浏览器交互实现。
- 扫码登录、同步按钮、增量采集、时间范围采集或其他抓取流程变更。
- 图片、头像、视频封面或视频的离线归档、缓存、清理和存储配额管理。
- 完整群成员列表、群成员采集、群成员数据表或群成员接口。
- 新增合并后的 `messageKind` 或 `mediaKind` 字段。
- 独立的群消息搜索接口或微博搜索接口。
- 搜索链接卡片、系统模板、文件名或任意结构化 JSON 字段。
- 为缺少封面的群视频下载视频并生成首帧缩略图。
- 将上游视频地址直接返回给调用方。
- 被转发微博的 `postUrl`。
- HTTP 多范围响应。
- 修改微博图片、群图片或头像的现有存储策略。

## Further Notes

- “本地查询”只表示列表和 Captured Content 来自本地数据库。媒体仍遵循现有 Media Proxy 约束，需要可用网络、Weibo API 和当前 Credential。
- 群消息接口的 `page`、`size` 从默认参数收紧为必填参数，属于有意的公开契约变化；实现时需要同步更新接口文档和现有调用测试。
- 视频 Range 代理必须验证微博上游返回的分片边界和 `Content-Length`。上游忽略范围或返回不一致分片时，不能把完整视频或错误字节伪装成 `206`。

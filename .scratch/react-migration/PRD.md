# React 前端迁移总纲

**Status:** ready-for-agent

日期：2026-10-12。
范围：整体迁移约束与首阶段边界。后续功能在进入对应阶段时细化。
用户已确认访谈决定与范围汇总，并授权形成首阶段规格与任务；前三票沿用此前讨论的开发通路、打包通路、post 最小阅读路径顺序。
状态仅表示规格可用于实施；实际进度以任务验收与验证记录为准。

## Problem Statement

当前前端按原生 JavaScript 工厂拆分功能，但模块仍同时管理可变状态、接口请求和 DOM 更新。
用户希望采用更常见的 React 技术栈，明确状态归属，降低后续维护和扩展成本。
迁移范围较大，一次交给模型过多规格或任务会增加漏项、范围扩张和集成错误。

## Solution

使用 React、TypeScript 和 Vite，保留两个独立页面入口。
开发时运行 Vite 与现有 Spring Boot，发布时将前端静态资源与后端打进同一个可执行 JAR。
先迁移 post，再迁移 chat；每页功能验收完成后才切换正式入口。
维护简短总纲，按阶段补充细节，逐票实现和验证。每票交付后由用户决定下一票。

## User Stories

1. 作为维护者，我希望使用 React 组件组织界面，使展示职责清楚。
2. 作为维护者，我希望使用 TypeScript 检查接口数据的使用，提前发现类型错误。
3. 作为开发者，我希望修改前端后能通过热更新查看结果，缩短反馈时间。
4. 作为开发者，我希望开发和发布使用相同的相对接口地址，避免维护两套请求代码。
5. 作为使用者，我希望继续通过两个熟悉的正式入口使用 post 与 chat。
6. 作为使用者，我希望 post 的博主、日期、阅读、搜索和媒体查看行为保持一致。
7. 作为使用者，我希望已实现的博主管理、按时段采集 Blogger Blog 和扫码入口保持可用。
8. 作为使用者，我希望 chat 的群选择、消息加载、发送和表态行为保持一致。
9. 作为使用者，我希望 Historical Browse 保持独立，不影响当前会话。
10. 作为使用者，我希望 View Refresh 和 Catch-up 补齐消息时保留阅读视口。
11. 作为使用者，我希望 Analysis、Return Celebration、沉浸阅读和既有特殊交互继续可用。
12. 作为使用者，我希望两页保持各自的皮肤、布局和主要尺寸。
13. 作为使用者，我希望只启动一个 Spring Boot JAR 就能加载页面并使用接口。
14. 作为使用者，我希望按页迁移时旧页面继续可用，并能通过旧发布产物回退。
15. 作为维护者，我希望每张任务票有明确验收证据，下一次会话能从真实进度继续。

## Implementation Decisions

- 单仓库、一个前端工程、两个页面入口；继续使用现有 Spring Boot 后端。
- 最终保留 `/post/index.html` 与 `/chat/index.html`。预览阶段分别使用 `/preview/post/index.html` 和 `/preview/chat/index.html`，避免覆盖正式页面。
- Maven 在 `generate-resources` 阶段执行前端构建，在 `process-resources` 阶段收集产物，使页面测试和打包能够读取同一份资源。
- 产物进入 Maven 的生成资源目录，并纳入 classpath 的 static 资源；源码目录保存手写源码，构建输出不写回源码目录。
- Vite 按实际接口路径代理请求，区分 HTML、前端资源和同名前缀的后端接口。开发代理兼容后续扫码长请求、媒体及 Analysis 流式请求。
- 明确区分服务端查询数据、页面协调状态、局部交互状态和 DOM 测量信息。可以推导的显示信息直接计算。
- 普通查询采用 TanStack Query；消息排序、合并、游标、Catch-up 与窗口状态由 chat 会话功能独立管理。查询默认策略必须符合原页面语义。
- 暂不引入客户端路由、全局状态库和统一皮肤框架。共享已有的通用行为，保持两套样式独立。
- 保持接口参数、响应、错误与日期时区语义；后端查询和数据库结构保持现状。
- post 的已实现功能作为迁移基线；仍待实现的定时 View Refresh 和新帖提示留在原任务中。
- 保持发送后通过采集进入本地库的语义；发送成功但采集失败时不自动重发。迁移不从发送响应直接构造权威消息。
- Historical Browse 独立于当前会话；一次性落底沿用现有 ADR，View Refresh 和 Catch-up 到达的新消息只提示，不自动移动视口。
- 保留现有窗口裁剪、动态媒体高度处理、流式分析节流、请求归属校验及资源清理能力。
- 富文本与 Markdown 继续经过清洗；旧 DOM 工厂和 React 分别拥有独立子树。
- 视觉保持现有皮肤、布局、字号与交互，接受细微差异；设计令牌作为唯一样式依据。
- 阻碍迁移的问题先记录，以独立修复提交处理。其他缺陷和未完成需求使用独立票。
- 切换前保留经过验证的旧 JAR、对应提交及配置说明。页面完成后清理被替代的旧代码，避免长期维护双实现。

## Testing Decisions

- 主要验证接口返回数据在真实浏览器中的用户可见行为，复用现有 Java Playwright 页面测试和其本地 HTTP 测试服务。
- 预览阶段新增针对 React 页面的小范围检查，正式入口切换后以原页面行为断言验收。
- 前端构建必须先于需要读取 classpath 静态资源的 UI 测试。构建产物中的模块、动态资源、图片与样式需要正确 MIME。
- 首票先运行现有两页定向回归建立基线。每票运行与改动相关的检查，在打包、整页切换和迁移结束处运行集成检查。
- 验证开发服务器代理与生产 JAR 两种路径。生产验证从干净构建产物启动，使用隔离数据库、不可用 Credential 和空自动采集群号；现有后台调度仍可能执行，缺少 Credential 时在构造请求头阶段拒绝外部采集请求。
- 以现有浏览器 HTTP 层作为查询替身，避免为了测试再创建一套后端抽象。关键纯逻辑在实际被提取时增加行为测试。
- 验证空数据、请求失败、旧响应隔离、登录失效、媒体及滚动等所属功能的风险。无需在首阶段提前实现全部场景。
- 检查两套皮肤、键盘可达性、长列表 DOM 规模、重复监听和轮询生命周期。验收行为与结果，不验收内部 Hook 数量或文件行数。
- 记录实际运行的检查及结果；迁移基线与各票进度以阶段计划中的最新证据为准。

## Out of Scope

页面视觉重设计、单页应用化、服务端渲染、多用户能力、数据库迁移、新后端协议、未完成的旧需求，以及与迁移无关的重构和缺陷修复。
长期保留新旧双版本入口和严格像素一致不属于本次交付目标。
